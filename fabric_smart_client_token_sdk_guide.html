2. Fabric Smart Client (FSC): The Node Runtime

Fabric Smart Client (FSC) (developed under Hyperledger Labs / LF Decentralized Trust) is an off-chain client node framework designed to overcome the limitations of classic client SDKs.

In standard blockchain clients, an application acts merely as a remote caller invoking chaincode. When multiple organizations need to negotiate, share confidential payloads, or jointly sign a transaction before submission, classic clients require external middleware, complex messaging queues, and custom coordination servers.

Core Capabilities of an FSC Node

  • Peer-to-Peer Communication Overlay: FSC nodes connect to each other directly via WebSockets or gRPC using mutual TLS. Node A can send messages directly to Node B without writing uncommitted data to the ledger.
  • Local State Management (Vault): Each FSC node maintains a local key-value store and transaction database to track its own unspent tokens, transaction drafts, and privacy parameters.
  • Identity & Endpoint Resolution: Decouples human-readable names (e.g., "alice", "owner2") from cryptographic public keys and network addresses.
  • Pluggable Settlement Drivers: An FSC node can drive transactions to Vanilla Fabric (via Fabric Gateway / peer APIs) or Fabric-X (via direct Orderer and Committer gRPC endpoints) with zero changes to high-level application logic.
💡
Key Distinction: An FSC Node is not a blockchain peer. It is an application-tier node that represents a participant (e.g., a Bank, an Issuer, a Merchant, or a User Wallet) operating on the periphery of the blockchain network.

3. The View Programming Model: Initiators, Responders & Sessions

The View is FSC’s fundamental programming primitive. Instead of writing fragmented request/response event handlers, you write a cohesive, linear Go function that represents a distributed protocol.

The Anatomy of a View

A View is any Go struct that implements the single view.View interface:

type View interface {
    Call(context view.Context) (interface{}, error)
}

Initiator View

The entry point that kicks off a distributed interaction. For example, when Alice calls POST /transfer, her node executes TransferView. The initiator opens a session with the counterparty node and coordinates the flow.

mgr, _ := viewregistry.GetManager(fscNode)
res, err := mgr.InitiateView(ctx, &TransferView{...})

Responder View

The recipient's reactive logic. When Dan's node receives an incoming message originating from an Initiator View, FSC automatically routes it to the registered Responder View (such as AcceptCashView).

reg := viewregistry.GetRegistry(fscNode)
reg.RegisterResponder(&AcceptCashView{}, &TransferView{})

P2P Sessions & The Communication Pipeline

Inside a View, parties exchange data using Sessions. When Alice calls session.Send(), the message is encrypted and sent directly over the P2P connection to Dan. Dan's node unblocks at session.Receive(), performs local verification, and sends back an acknowledgment or cryptographic signature.

⚡
Why this is revolutionary: Multi-round cryptographic exchanges (e.g., identity derivation → selective disclosure → zero-knowledge proof verification → co-signing) take place entirely off-chain. The blockchain only receives the final, valid, fully-endorsed transaction package.

4. The Token SDK (Panurus): Private UTXOs & ZKPs

The Token SDK (formerly developed by IBM Research and Hyperledger Labs, now maintained under LF Decentralized Trust as Panurus) builds on top of FSC to provide a production-grade tokenization framework.

1. The UTXO Model vs. The Account Model

Most smart contract token standards (such as Ethereum's ERC-20) use an account-based balance table (balances[address] = amount). This causes two major issues in enterprise settings:

  • Concurrency Bottlenecks: Multiple concurrent transfers involving the same address conflict on the read/write set (MVCC read conflict in Fabric).
  • Privacy Exposure: Every account's current balance and transaction amount are visible to any node validating state.

The Token SDK instead employs the UTXO (Unspent Transaction Output) model. Value is stored in discrete cryptographic "coins". To transfer 100 TOK from a 1,000 TOK coin, the 1,000 TOK coin is consumed (spent), and two new coins are minted: 100 TOK for the recipient, and 900 TOK returned to the sender as "change".

2. Zero-Knowledge Proofs: ZKAT DLOG

The Token SDK supports the ZKAT DLOG (Zero-Knowledge Audit-Tokens Discrete Logarithm) driver:

Pedersen Commitments

The token value \(v\) is hidden inside a cryptographic commitment: $$\mathcal{C} = g^v \cdot h^r$$ where \(r\) is a blinding factor known only to the owner. The ledger records \(\mathcal{C}\), concealing the exact amount.

Zero-Knowledge Conservation of Value

The sender generates a mathematical proof that: $$\sum \text{Inputs} = \sum \text{Outputs}$$ Verifiers and endorsers can verify mathematically that no tokens were created out of thin air, without knowing what the inputs or outputs actually evaluate to.

Furthermore, owner identities are masked using Idemix (Identity Mixer) or pseudonymous one-time keys, making it impossible for network participants or eavesdroppers to link transactions to physical corporate entities.

5. End-to-End Walkthrough of a Private Transfer

Here is the step-by-step lifecycle of an off-chain private token transfer between Alice (Owner 1) and Dan (Owner 2):

1

Triggering the Transfer View

Client sends an HTTP request: POST /owner/accounts/alice/transfer to Owner 1. The HTTP handler instantiates and triggers TransferView inside the FSC runtime.

2

Off-Chain Pseudonym Exchange

Alice’s view initiates an off-chain session with Dan's node. Alice calls RequestRecipientIdentity(dan). Dan's node fires AcceptCashView, generates a fresh, pseudonymous public key, and returns it over WebSockets. No observer can correlate this key to Dan.

3

Local UTXO Selection & ZKP Construction

Alice's Token SDK searches her local database for sufficient unspent tokens. It constructs a transaction envelope, computes the output commitments (recipient amount and change), and generates the zero-knowledge proofs.

4

Recipient Validation & Acceptance

Alice transmits the drafted transaction to Dan off-chain. Dan's AcceptCashView inspects the outputs, confirms he is indeed receiving the promised tokens, and signs an acceptance token witness back to Alice.

5

ZKP Endorsement Gathering

Alice’s view sends the transaction to the Endorser Service via ttx.NewCollectEndorsementsView. The endorser verifies that the ZKP proofs are mathematically sound and signs the endorsement proposal.

6

Ordering & Ledger Finality

Alice submits the transaction envelope to the Ordering Service (Raft in Fabric 3; Arma BFT in Fabric-X). Once committed to the block, Alice and Dan receive finality notification events. Both nodes transition the transaction state to Confirmed and update their local wallet balances.

6. Vanilla Fabric vs. Fabric-X: Full Technical Comparison

While the high-level application code (FSC Views and Token SDK) remains virtually identical, the underlying architecture between Vanilla Fabric (2.x / 3.x) and Fabric-X represents a profound paradigm shift.

Architectural Dimension Vanilla Hyperledger Fabric (2.x / 3.x) Hyperledger Fabric-X
Peer Architecture Monolithic Peer Node: A single process handles simulation, endorsement, gossiping, ledger storage, validation, and committing. Disaggregated Microservices: Endorsers, Validators, Committers, and Query Services run as independently scalable services.
Smart Contract (Chaincode) Execution Runs as Docker containers managed by peer nodes using the classic Chaincode Shim / External Builder interface. Standalone Endorser Services: Endorsers run outside peer nodes as standalone gRPC services implementing the Executor interface.
Consensus & Ordering Service Raft (CFT): Crash Fault Tolerant consensus. Orders full transaction payloads. Subject to bandwidth bottlenecks. Arma (BFT): Sharded Byzantine Fault Tolerant consensus. Orders compact transaction digests across Router, Batcher, Consenter, and Assembler nodes.
Throughput & Scalability Bottlenecks at ~3,000 – 4,000 TPS due to serial validation and Raft block replication. 200,000 – 400,000+ TPS: Horizontal scaling of individual microservices designed for national-scale payment systems.
State Database & Storage Embedded LevelDB or CouchDB inside peer containers. Heavy read/write contention during peak traffic. Enterprise PostgreSQL State DB: Offloaded to external relational databases with dedicated read-only Query Services.
Token SDK Driver Uses fabric.NewGenericDriver. Requires traditional chaincode deployment cycle (package, install, approve, commit). Uses fabricx.NewDriver + tms.DeployerService. Token parameters are committed directly to the namespace via /endorser/init.

How the Code Switches Between Vanilla Fabric and Fabric-X

In the repository, the switch between platforms is achieved seamlessly at compile time using Go build tags:

Vanilla Fabric (common/sdk_3.go)

//go:build !fabricx

package common

import (
    "github.com/LFDT-Panurus/panurus/token/services/network/fabric"
    // ...
)

func (p *SDK) Install() error {
    // Injects classic Fabric network driver
    p.Container().Provide(fabric.NewGenericDriver, 
        dig.Group("network-drivers"))
    // ...
}

Fabric-X (common/sdk_x.go)

//go:build fabricx

package common

import (
    "github.com/LFDT-Panurus/panurus/token/services/network/fabricx"
    "github.com/LFDT-Panurus/panurus/token/services/network/fabricx/tms"
    // ...
)

func (p *SDK) Install() error {
    // Injects Fabric-X driver and direct submitters
    p.Container().Provide(fabricx.NewDriver, 
        dig.Group("network-drivers"))
    p.Container().Provide(tms.NewSubmitterFromFNS, 
        dig.As(new(tms.Submitter)))
    // ...
}

7. Summary: Why This Architecture Matters

The combination of Fabric Smart Client, the View Framework, and the Token SDK over Fabric-X represents the state of the art in enterprise blockchain engineering:

Complete Privacy

Balances, identities, and transaction values never touch the shared ledger in plaintext. Regulatory compliance is satisfied without compromising confidentiality.

Modular Clean Architecture

Developers write standard, imperative Go workflows (Views) without wrestling with low-level gRPC streams, cryptographic curves, or blockchain protocols.

Future-Proof Portability

The identical business code runs on local test containers, classic Fabric 3.x clusters, or enterprise-scale Fabric-X networks simply by swapping build flags.
